# 源码文件行数门禁与拆分指南

> **第一读者是 AI 编程代理。** 在新建源码文件、或向既有文件添加代码之前先读完本文；
> 任务涉及的文件若已达/接近上限，拆分是任务的一部分（先拆后加）。
> 门禁工具：`tools/source-quality/`（统计 / 校验 / 基线）；配套工具使用说明见 [工具 README](../../tools/source-quality/README.md)。

## 一、为什么有这条门禁

1. **上下文成本**：AI 编程代理与人类在修改文件前都要读文件；单文件越长，读取成本越高、且更容易漏看漏改（错误往往出在没读到的部分）。
2. **耦合度信号**：一个文件持续膨胀，通常说明它承担了多个职责——这正是最需要拆分的时候，而不是继续加代码的时候。
3. **变更可审性**：几百行的 diff 里藏一个行为变化很难被发现；拆分后每个文件的改动意图更清晰。
4. **并行协作**：本仓库按任务并行推进，文件越大，多任务碰同一文件的冲突面越大。

门禁的立场一句话：**超限文件禁止继续增长；要加代码，先拆。**

## 二、门禁口径（先看这一节）

### 2.1 指标定义

- **有效行 = 非空行**（注释行计入、纯空行不计）。
- 选这个口径的原因：精确、易核对（`grep -cve '^[[:space:]]*$' 文件` 即可人工复核），且注释同样是文件体积与维护成本的一部分。
- 报告中的「注释 / 代码行拆分」是对分析用的近似值，**不参与门禁判定**。

### 2.2 各语言上限

| 语言 | 扩展名 | 上限（有效行） | 说明 |
| --- | --- | --- | --- |
| Rust | `.rs` | 500 | 基数；**内联 `#[cfg(test)] mod` 测试模块不计入**（见 2.3） |
| TypeScript | `.ts` / `.tsx` | 500 | 基数；按域拆分手段成熟 |
| JavaScript | `.js` / `.mjs` / `.cjs` | 500 | 基数；含 `tools/` 下脚本（工具自身同样受门禁约束） |
| Vue SFC | `.vue` | 600 | 单文件承载 template + script + style 三段，比纯逻辑文件天然更长，予以放宽 |
| CSS | `.css` | 600 | 样式声明无控制流，且本仓库样式文件数量少；与 Vue 保持一致便于心智统一 |

上限定义在 [tools/source-quality/config.json](../../tools/source-quality/config.json)；调整须走 3.3 节流程。

### 2.3 Rust 测试模块特例

- 门禁**不统计**文件末尾的内联测试模块：以「`#[cfg(test)]` 属性行 + 紧邻的 `mod` 声明」为分界，分界之后视为测试区。
- 目的：避免惩罚测试覆盖、鼓励就近写测试。测试行数单独统计；测试模块超过 **400 行**会进入报告的「测试模块偏大」清单，建议拆到独立测试文件（手法见 5.1.3）。
- 局限（按保守方向处理）：其他形式的 `#[cfg(test)]`（例如修饰某个测试专用方法）不构成分界，按代码计。
- `src-tauri/tests/` 等独立测试文件属于普通源码文件，正常计入。

### 2.4 扫描范围

- 纳入：`src/`、`src-tauri/`、`tools/` 下所有已登记语言的源码文件；
- 排除：`node_modules`、`target`、`gen`、`dist`、`tmp` 及配置类扩展名（`.json` / `.md` / `.toml` / `.lock` 等，见 config.json `ignoreExt`）；
- 扫描到未纳管扩展名（如新引入 `.scss`）时报告会在末尾提示，需在 config.json 登记后方可纳入门禁（流程见 3.3）。

### 2.5 基线机制（历史遗留文件）

引入门禁时，仓库已存在一批超限文件。它们被登记在 [tools/source-quality/baseline.json](../../tools/source-quality/baseline.json)：

- **基线内文件**：允许保持现状，**不得增长**——任何净增长都会导致门禁失败；
- **文件拆分达标后**：运行 `pnpm quality:baseline` 清理其条目（也可以顺便把仍在超限但已缩小的文件更新为更小额度）；
- 基线条目**只允许缩小或清理**，增大需 `--force` 并在提交信息中说明理由（AI 编程代理默认无此权限，见 3.3）。

## 三、命令与执行时机

### 3.1 命令速查

| 命令 | 用途 | 退出码 |
| --- | --- | --- |
| `pnpm quality:stats` | 统计报告：各语言汇总、超限清单、长函数预警、测试模块偏大清单 | 恒 0 |
| `pnpm quality:stats --json` | 机器可读版本（AI 编程代理建议用这个，按 `files[].path` 过滤即可查单个文件） | 恒 0 |
| `pnpm quality:gate` | 门禁校验：任何新增超限 / 基线内增长 → 失败 | 0 通过 / 1 未通过 / 2 错误 |
| `pnpm quality:baseline` | 重建基线（拆分完成后清理 / 缩小条目） | 0 成功 / 2 被拒（条目增大） |

> JSON 管道提示：`pnpm` 会在 stdout 打印任务横幅；要把 JSON 直接交给其他程序解析，请用 `pnpm --silent quality:stats --json`（或直接 `node tools/source-quality/cli.mjs report --json`）。
> 报告文件提示：`--out[=路径]` 可把报告写入文件，**默认写入 `tmp/`**（`tmp/quality-report.json|txt` / `tmp/quality-check.json|txt`，tmp/ 已 gitignore）；报告属于临时产物，**不要提交到仓库**。

### 3.2 执行时机

- **开工前**：`pnpm quality:stats --json`，确认任务涉及的文件是否超限或接近上限——提前知道要拆分，比写完被测出超限更省事；
- **每次提交前**：`pnpm quality:gate` 必须通过（与 `pnpm lint`、`pnpm typecheck` 同列，见 AGENTS.md 3.5）；
- **拆分完成后**：`pnpm quality:baseline` 清理已达标条目（属于拆分工作的一部分）。

### 3.3 禁止事项（AI 编程代理特别条款）

- 不得自行放宽 `config.json` 中的 `limit`；
- 不得使用 `update-baseline --force` 为超限文件加额度；
- 不得通过改口径、改排除规则等方式绕过门禁。
  以上调整均属流程变更，需人类确认后在提交信息中说明理由。

## 四、AI 编程代理工作流（核心）

当任务要求向源码添加/修改代码时，按以下顺序执行：

1. **测量**：`pnpm quality:stats --json`，过滤任务相关文件，读出各自 `gated`（有效行）与 `limit`。
2. **判定**：
   - 文件未超限、且本次改动后仍在限内（建议预留 10% 余量）→ 直接改；
   - 文件已达**上限的 70%**（Rust / TS / JS ≥ 350 行，Vue / CSS ≥ 420 行）→ 本次改动前先规划拆分，避免下一次任务被迫拆分；
   - 文件超上限、或改动会使其超限 → **先拆分，再做功能改动**（拆分单独提交，见第 6 节）。
3. **设计拆分方案**：先列「这个文件里的关注点清单」，按职责/域划分目标模块；每块目标 **200–450 行**；每块必须有独立职责，不要按行数机械切割。
4. **增量搬移**：一次只移动一个关注点；搬移过程**不改行为**（纯移动 + 必要的 `use` / `import` 调整）；每移动一步跑一次测试。
5. **保持公开 API 稳定**：用 re-export 保持原有模块路径可用（Rust `pub use`，TS `export * from`，Vue 组件路径保持入口文件不变），这样调用方零改动、拆分 diff 可审。
6. **验证**：跑对应测试（`cargo test --manifest-path src-tauri/Cargo.toml` / `pnpm test`）+ `pnpm quality:gate`（必须为 0）。
7. **收尾**：`pnpm quality:baseline` 清理/缩小达标条目；提交拆分（提交信息说明「拆分自 X，为 T-XXX 做准备」，纯拆分与功能改动分开提交，AGENTS.md 3.6）。

### 特殊场景

- **任务必须修改基线内文件（如 T-XXX 要在 scene.rs 里加功能）**：择优处理——能先拆拆先（推荐）；若本次仅做小修（不增长），可在基线额度内完成；**任何净增长都必须先拆**。
- **新建文件**：从第一天就按职责命名（见各语言手法），预估超 350 行时直接拆成模块目录而不是单文件。
- **拆完仍超限**（如 2000 行的文件一次拆不完）：分多次任务渐进拆分；每次拆完运行 `pnpm quality:baseline` 把条目缩小到当前值，形成 ratchet 收敛。

## 五、各语言拆分手法

### 5.1 Rust（`src-tauri/src/`）

#### 5.1.1 服务文件 → 模块目录

```text
services/scene.rs（1196 行）
  ↓ 拆为
services/scene/
  ├── mod.rs        # 只做组织与 re-export：pub use rules::*; pub use matcher::*;
  ├── rules.rs      # 场景规则数据与解析
  ├── matcher.rs    # 匹配算法
  └── types.rs      # 共享类型
```

- `mod.rs` 保持原 `services::scene::XxxService` 等路径不变（re-export），其他模块的 `use` 零改动；
- 拆分点选择：纯函数 / 数据结构优先搬（依赖少）；带状态的方法放最后并检查字段可见性；
- 若多个模块需要访问同一 struct 的内部字段，把字段收窄为 `pub(super)` / `pub(crate)`，不要开 `pub`。

#### 5.1.2 大函数拆分

报告「长函数预警」（≥ 80 行）是线索清单。对一个超长函数：

1. 识别内部的「段落」（通常已是注释分隔的若干阶段）；
2. 每段提取为私有辅助函数：`fn phase_a(...) -> Result<...>`，主函数变成 5–15 行的高层流程；
3. match 分支过大时，分支体提取为独立函数或子枚举方法。

#### 5.1.3 内联测试模块拆到独立文件

```rust
// services/scene.rs 末尾
#[cfg(test)]
mod tests; // 指向 services/scene/tests.rs

// services/scene/tests.rs
use super::*; // 与内联写法完全一致
[原 mod tests { ... } 的内容去掉外层大括号]
```

- 测试文件路径规则：`foo.rs` 的 `mod tests;` 查找 `foo/tests.rs`（与 `foo.rs` 并列的目录）；
- 也允许 `#[path = "scene_tests.rs"] #[cfg(test)] mod tests;` 平铺命名；
- 拆分属纯搬移：`cargo test` 必须全绿。

#### 5.1.4 命令层 / 平台层

- `commands/`：按业务域分目录（`commands/ai/`、`commands/dict/`），每个 `invoke` 命令所在函数保持薄（调用服务层）；
- `platform/`：`mod.rs` 做特质定义与 re-export，具体实现按平台文件拆分（本仓库已有此结构，遵循即可）。

### 5.2 TypeScript（`src/`）

#### 5.2.1 按域拆文件 + barrel 出口

```text
api/types.ts（480 行）
  ↓ 拆为
api/types/
  ├── index.ts     # export * from './asr'; export * from './ai'; ...
  ├── asr.ts
  ├── ai.ts
  └── dict.ts
```

- `index.ts` 只做 re-export，原 `@/api/types` 导入路径零改动；
- 类型、常量、工具函数分开暂存（`types.ts` / `constants.ts` / `utils.ts`），不混职责。

#### 5.2.2 i18n 文案按命名空间拆

`src/i18n/zh-CN.ts` / `en-US.ts` 为嵌套命名空间对象（`app` / `shell` / `nav` / `coding` / `dict` …）：

```text
i18n/zh-CN.ts（644 行）
  ↓ 拆为
i18n/zh-CN/
  ├── index.ts     # import { app } from './app'; ... export const zhCN = { app, shell, ... }
  ├── common.ts    # app / shell / nav 等骨架文案
  ├── coding.ts
  ├── dict.ts
  └── ...
```

- 保持 `index.ts` 导出的对象结构与类型不变（键路径不变，组件侧 `t('...')` 零改动）；
- 中英文两侧采用**相同的命名空间文件划分**，便于对照翻译。

#### 5.2.3 Store / 组合式逻辑

- Pinia store 超限：store 只保留状态与动作签名，纯逻辑提取为独立 `xxxOps.ts` 或 composable；
- `src/utils/`：按领域聚合，避免一个 `utils.ts` 什么都装。

### 5.3 Vue SFC（`src/views/`、`src/components/`）

#### 5.3.1 大页面 → 目录 + 子组件

```text
views/coding/ScenesView.vue（875 行）
  ↓ 拆为
views/coding/scenes/
  ├── index.vue        # 路由入口：布局 + 组装子组件
  ├── SceneRuleList.vue    # 列表区
  ├── SceneRuleEditor.vue  # 编辑表单
  └── useSceneRules.ts     # 组合式逻辑（数据获取、校验、保存）
```

- 路由文件指向 `index.vue` 即可，路由配置零改动（或仅改一个路径字符串）；
- 优先提取顺序：独立的模板块（对话框 / 表单 / 列表）→ 数据逻辑（转 composable）→ 仅剩布局时模板自然瘦身。

#### 5.3.2 逻辑入 composable

- `script setup` 中超过 ~150 行的逻辑部分应进 `useXxx.ts`：状态、watch、请求、校验各自成函数；
- composable 放组件同目录（局部使用）或 `src/composables/`（跨组件复用）。

#### 5.3.3 样式

- 仅在单组件使用的 `<style scoped>` 保留在 SFC；跨组件共用样式抽到 `src/styles/`；
- 单个 SFC 的样式段超过 ~200 行时，同样按 5.4 的思路挪出。

### 5.4 CSS（`src/styles/`）

- 按「主题基础 / 全局布局 / 组件覆写」分区；`primevue-theme.css` 只放主题变量与 PrimeVue 覆写，业务样式另起文件；
- 新增大块样式前先问：属于哪个组件/域？放对应文件而不是挤进 `global.css`。

## 六、与仓库工作流的衔接

1. **提交粒度**：拆分为纯搬移提交（"refactor: 拆分 X 模块为 Y/Z"，附动机与 SPEC 关联），功能改动单独提交；单个提交只做一件事（AGENTS.md 3.6）。
2. **与 SPEC 任务的关系**：拆分可以是任务的一部分（当任务必须触碰超限文件时），优先「先拆后加」；大重构式拆分建议独立成任务或先与用户确认范围。
3. **上限 / 口径变更**：属流程变更（见 3.3），由人类决定；变更时同步更新本文档与 [quality/README](./README.md)。
4. **准入检查**：向 `src/`、`src-tauri/`、`tools/` 引入新语言（如 `.scss`）时，报告会在「未纳管扩展名」处提示；登记 config.json 后才受门禁保护——登记操作同样需要人类确认。

## 七、拆分反模式（不要做）

- **凑数切割**：把一段连续逻辑从中间硬切两半（必然产生跨文件来回跳）；
- **碎片化**：拆出 < 50 行且无独立职责的微文件（该合并回父文件或相邻模块）；
- **搬家夹带改动**：纯搬移提交里修改行为（拆分必须行为等价，测试全绿是证据）;
- **绕过门禁**：放宽上限、`--force` 加基线、把文件塞进排除规则；
- **只拆不接头**：拆完不改 re-export，导致调用方大规模改导入路径（先保 API 再谈其它）；
- **拆完不跑测试**：搬移错误只有测试能发现。

## 八、常见问题（FAQ）

**Q1：我的任务恰好要改一个基线内文件（例如要在 scene.rs 里加 100 行），怎么办？**

三条路，按优先级：① 先拆分该文件把目标区域挪出来，再在子模块里实现（推荐，拆分计入本任务）；② 若本次改动不增长（等价重构），可直接做；③ 若确需净增长且无法拆分（极少见），停下来向用户说明并申请 `--force` 更新基线——不要擅自执行。

**Q2：注释和空行怎么算？**

空行不算；注释算有效行。给文件加大量注释导致超限时，优先考虑：注释是否应转化为文档（doc/ 或 README），代码是否可拆分。

**Q3：Rust 的测试算行数吗？**

文件末尾内联 `#[cfg(test)] mod`（含 `mod tests;` 独立文件形式）不计入；其他位置的 `#[cfg(test)]`、以及 `src-tauri/tests/` 下的独立测试文件计入。内联测试模块 > 400 行建议拆独立文件。

**Q4：Vue 文件为什么上限是 600？**

SFC 一文件含模板、逻辑、样式三段，硬套 500 会迫使很多页面无谓拆分；600 对应「三段各约 200 行」的合理结构。逻辑段仍建议 ≤ 150 行进 composable。

**Q5：如何查某个具体文件当前多少行？**

`pnpm quality:stats --json`，在 `files` 数组里找 `path`；`gated` 即门禁口径行数。或 `grep -cve '^[[:space:]]*$' <文件>` 人工复核（Rust 需再减去 `#[cfg(test)]` 之后的部分）。

**Q6：新建语言文件（例如工具脚本）会不会被误判？**

`tools/` 下 `.mjs` 已登记为 JavaScript（上限 500）；未登记扩展名不会被门禁判定，但会在报告中提示——提示即待办：登记或排除，二者都需要人类确认。
