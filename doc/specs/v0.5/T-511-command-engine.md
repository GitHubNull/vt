## 1. 目标与范围

### 1.1 目标

在后处理管线中接入编程口令 Stage（CommandEngine）：把识别文本中的口令片段（命名风格 / 符号 / 按键）解析为结构化指令并执行转换或按键动作。

### 1.2 范围内

- CommandEngine Stage：注册进 PostProcess 管线（位于替换词典之后）；
- 口令解析框架：分词 → 口令识别（词表驱动）→ 指令 AST → 执行器（文本转换 / 按键动作）；
- 口令词表数据结构（可扩展，v1.x 自定义口令复用）；
- 按键动作出口：与 InjectService 打通（按键事件注入，区别于纯文本上屏）；
- Stage 独立开关（产品原则 3）；误转换防护：口令仅在明确语境触发（规则见 PRD 3.2 节）；
- 场景联动：终端场景下按键动作受终端安全保护约束（接口预留，T-515 实现）。

### 1.3 范围外

- 具体口令词表与转换规则（T-512 命名风格、T-513 符号、T-514 按键）；
- 终端安全保护（T-515）；
- 自定义口令（v1.x）。

## 2. 需求依据

- PRD 3.2.2 ~ 3.2.4 节：口令的用户故事与业务规则；
- NFR-A-04/05/06：口令正确率与误触发指标（框架设计需支持精确匹配与误触发控制）；
- [tech/05](../../tech/05-core-pipeline.md) 5.1 管线结构；
- [tech/04](../../tech/04-backend.md) 4.4 CommandEngine。

## 3. 技术上下文

- 新建：`src-tauri/src/services/command_engine.rs`（Stage + 解析器 + 执行器）；
- 复用：T-011 管线框架、T-007 InjectService（扩展按键注入）、T-501 场景信息；
- InjectService 需新增 `press_key` 能力（单键 / 组合键），平台层扩展。

## 4. 任务步骤

1. 定义口令 AST：`Command { Transform(style, payload) | Symbol(sym) | KeyPress(key, modifiers) | Literal(text) }`；
2. 实现解析器：输入文本 → 口令词表匹配 → AST 序列；匹配规则（词边界、语境要求）按 PRD 3.2 节；
3. 实现执行器：AST → 输出文本片段 + 按键动作序列；
4. InjectService 扩展：`press_key`（平台层三平台实现），与文本注入同会话顺序执行；
5. Stage 接入管线并绑定独立开关；
6. 单元测试：解析器（口令 / 非口令边界）、执行器、按键动作顺序；
7. 联调：用临时口令词表验证端到端（识别文本 → 口令执行）。

## 5. 验收标准

- [ ] 管线中 CommandEngine Stage 位于替换词典之后，可独立开关；
- [ ] 口令 AST 解析正确：口令片段与非口令片段边界清晰（PRD 3.2 示例逐条）；
- [ ] 按键动作经 InjectService 正确注入目标应用（编辑器实测）；
- [ ] 非口令语境的普通文本不被误转换（误触发防护测试集）；
- [ ] Stage 关闭时识别原文直出；
- [ ] 三平台手动验证按键注入通过。

## 6. 测试要求

- `cargo test`：解析器、执行器、AST；
- 手动验证：编辑器中口令转换与按键注入。
