# 第 1 章 总体架构

> 本章描述 VT 桌面端的整体架构：进程模型、分层结构、模块划分与模块间通信方式。
> 需求依据：PRD 第 2 章（信息架构）、第 5 章（非功能需求）。

## 1.1 架构总览

VT 桌面端是一个 **Tauri 2 应用**：Rust 编写的原生后端（单进程）+ 运行在系统 Webview 中的 Vue 3 前端（多窗口）。选择 Tauri 2 的核心动机：

- **性能与体积**：满足 NFR-P-06（空闲内存 ≤150 MB，不含模型）与 NFR-P-09（安装包 ≤120 MB），Electron 类方案无法达标；
- **系统能力**：全局快捷键、文本注入（模拟输入）、托盘、麦克风采集都需要原生 API，Rust 生态（`global-shortcut`、`enigo`、`cpal` 等）覆盖三平台；
- **隐私优先**：本地 ASR 推理（Rust 直接加载模型）与"录音不出本机"的承诺天然契合。

## 1.2 进程与窗口模型

### 1.2.1 单进程多窗口

- 整个应用只有**一个操作系统进程**（Tauri 主进程），所有窗口共享同一个 Rust 后端实例与 tokio 运行时；
- 前端有三个窗口，按需创建与销毁：

| 窗口 | 生命周期 | 特性 |
| --- | --- | --- |
| 设置主窗口 | 用户打开时创建，关闭时销毁（托盘常驻不退出） | 普通窗口，三栏式设置中心 |
| 语音输入小窗 | 用户通过托盘 / 快捷键唤起，可常驻 | 轻量窗口，一个麦克风按钮 |
| 录音悬浮球 | 录音开始时创建，录音结束销毁 | 无边框、透明、置顶、**不抢焦点**（`focusable: false`） |

- 悬浮球"零打扰"（产品原则 2）由窗口创建参数保证：不激活、不获取输入焦点，实现见 [第 3 章](./03-frontend.md) 与 [第 9 章](./09-cross-platform.md)。

### 1.2.2 为什么不用多进程

ASR 推理放在进程内（动态库 / crate 直接调用）而非独立进程，理由：避免 IPC 拷贝音频帧的开销（NFR-P-03 要求 ≤10 秒语音 P95 上屏 ≤800 ms）；崩溃隔离需求由 NFR-R-02（崩溃自动重启）在进程级兜底。

## 1.3 后端分层

Rust 后端自上而下分三层，依赖方向单向向下：

```
命令层（commands/）   ── Tauri Commands，参数校验、权限检查、调用服务层
   ↓
服务层（services/）   ── 业务逻辑，tokio 异步任务，跨窗口事件广播
   ↓
平台适配层（platform/）── trait 抽象 + Windows / macOS / Linux 条件编译实现
```

- **命令层**：唯一的前端入口。每个 `#[tauri::command]` 函数做参数校验（边界校验只在这一层与外部接口处做），调用服务层，返回 `Result<T, AppError>`；
- **服务层**：核心业务。各服务持有自己的状态（`tokio::sync::RwLock` / 通道），服务间通过消息通道解耦，不直接互相持有引用；
- **平台适配层**：所有操作系统差异收敛在此。对上与对下都是稳定 trait，三平台用 `#[cfg(target_os)]` 条件编译提供实现。

详细设计见 [第 4 章](./04-backend.md)。

## 1.5 模块间通信

### 1.5.1 前端 ↔ 后端

- **请求响应**：前端 `invoke('cmd_name', args)` → 命令层 → 返回 Promise；
- **后端主动推送**：Tauri Event（`emit` / `listen`），用于录音状态、音量电平、设备连接状态等实时事件；
- 前后端通信的统一封装与命名约定见 [第 3 章](./03-frontend.md) 第 3.5 节。

### 1.5.2 服务间通信

- 服务间通过 `tokio::sync::mpsc` 通道传递消息（如 AudioService → AsrService 的音频帧流）；
- 状态查询走服务暴露的只读方法（`RwLock` 读锁），禁止服务间直接修改对方状态；
- 核心链路的完整时序见 [第 5 章](./05-core-pipeline.md)。

### 1.5.3 外部通信

| 通道 | 协议 | 用途 | 安全约束 |
| --- | --- | --- | --- |
| AI 供应商 | HTTPS | 文本后处理（用户配置后） | 仅文本，敏感信息先打码（NFR-PR-03、NFR-S-03） |
| 移动设备 | WebSocket（局域网 / USB） | 音频流、控制键、状态 | 配对令牌 + 加密传输（NFR-S-08/09） |
| MCP 客户端 | MCP over HTTP（本机回环） | AI 智能体语音提问等 | 默认关闭、仅 127.0.0.1、令牌校验（NFR-S-04） |
| 更新服务器 | HTTPS | 版本检查与更新包 | 只发版本号 / OS / 架构；签名校验（NFR-PR-06、NFR-S-06） |

## 1.6 关键架构决策记录（ADR 摘要）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| ADR-1 | Tauri 2 而非 Electron | 内存与安装包体积指标（NFR-P-06/09） |
| ADR-2 | ASR 推理进程内 | 避免音频 IPC 开销，满足上屏延迟（NFR-P-03/04） |
| ADR-3 | 服务间消息通道而非共享状态 | 并发安全、可测试性；避免锁竞争 |
| ADR-4 | 平台差异收敛在 platform/ 层 trait | 业务代码零 `cfg`，差异可单测（mock 实现） |
| ADR-5 | 移动设备通道用 WebSocket 而非自定义 TCP | tokio-tungstenite 成熟、移动端（Android）实现简单、未来可平滑升级 WSS |
| ADR-6 | 移动客户端独立仓库 vt-mobile，仅 Android | 两端分别版本化；iOS 因开发者账号成本暂缓（产品决策 2026-10-09） |
