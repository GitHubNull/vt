## 二、阶段依赖关系

```
v0.1 MVP（核心链路 + 工程地基）
   │
   ▼  依赖：核心链路稳定、配置/日志/平台层可复用
v0.5 Beta（编程与 AI 能力）
   │
   ▼  依赖：后处理管线 Stage 抽象、供应商抽象
v1.0 正式版（MCP、移动麦克风、隐私完善）
   │
   ▼  依赖：协议稳定、安全机制就绪
v1.x（增强与生态）
```

规则：后一阶段的任务可以**并行准备**（文档、协议设计），但代码合入以阶段顺序为准；跨阶段依赖在各子路线图的"依赖"列标注。

## 三、任务编号约定

- 任务编号：`T-<阶段>-<序号>`，v0.1 阶段简写为 `T-001` ~ `T-016`；v0.5 起为 `T-501+`、v1.0 为 `T-1001+`（编号段在对应子路线图中定义）；
- 每个任务对应一个 SPEC 文件：`doc/specs/<阶段>/T-xxx-<语义化名>.md`；
- 任务粒度：一个任务是一次 AI 代理会话可完成的独立交付（有明确验收标准、可独立验证）；
- 任务状态在子路线图中维护：⬜ 未开始 / 🔶 进行中 / ✅ 完成。

## 四、执行规则（给 AI 编程代理）

1. **入口**：从当前阶段的子路线图选取"依赖已满足"的任务，打开其 SPEC 执行；
2. **SPEC 即合同**：验收标准逐条满足才算完成；SPEC 与 PRD 冲突时停下来报告，不得自行取舍；
3. **产品原则不可违背**：见 AGENTS.md 3.2（本地优先、零打扰、结果可预期、安全第一、隐私优先）；
4. **不估算时间**：任何文档与代码中不写"预计 X 天"类内容；
5. **文档同步**：实现导致技术方案变化时，先更新 `doc/tech/` 对应章节再改代码；需求变化先改 PRD；
6. **禁止事项**：不引入音视频转录（已决策移除）；不为 iOS 编写任何移动端内容（Android only）；不在日志中写密钥与用户文本。
